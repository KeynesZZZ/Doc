# 【笔记】网络基础知识

现有网络文档直接进入了 Socket 编程实战，缺少理论铺垫。本文补全基础层：分层模型、协议原理、基础设施、游戏架构选型，作为网络系统专题的知识基石。

## 一、网络分层模型

### 1.1 两种模型对比

```
┌──────────────────────────────────────────────────────────────┐
│                    两种分层模型                               │
├──────────────────────────────────────────────────────────────┤
│                                                              │

│  ├─────────────────────┤        │  HTTP, DNS, WS      │      │
│  │ 6. 表示层           │        │  SSL/TLS            │      │
│  │    SSL/TLS, 编码    │        │                     │      │
│  ├─────────────────────┤        ├─────────────────────┤      │
│  │ 5. 会话层           │        │  传输层             │      │
│  │    Socket           │        │  TCP, UDP           │      │
│  ├─────────────────────┤        ├─────────────────────┤      │
│  │ 4. 传输层           │        │  网络层             │      │

│  ├─────────────────────┤        ├─────────────────────┤      │
│  │ 3. 网络层           │        │  网络接口层         │      │

│  ├─────────────────────┤        │                     │      │
│  │ 2. 数据链路层       │        │                     │      │
│  │    以太网, ARP      │        │                     │      │
│  ├─────────────────────┤        │                     │      │
│  │ 1. 物理层           │        │                     │      │
│  │    电缆, 光纤       │        │                     │      │
│  └─────────────────────┘        └─────────────────────┘      │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 游戏开发各层关注点

| 层级 | 游戏开发关注什么 |
|------|-----------------|
| **应用层** | 消息协议设计（Protobuf/JSON）、RESTful API、WebSocket |
| **传输层** | TCP vs UDP 选择、可靠 UDP 实现（KCP/ENET） |
| **网络层** | IP 地址、NAT 穿透、防火墙 |
| **网络接口层** | 一般不关心（除非做底层网络引擎） |

> **实践建议**：游戏开发绝大多数时间在**应用层和传输层**工作，理解 TCP/UDP 原理是最核心的前置知识。

## 二、TCP 深入

### 2.1 TCP 核心特性

```
TCP（传输控制协议）— 面向连接、可靠传输

┌──────────────────────────────────────────────────────────────┐
│                       TCP 核心机制                           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 面向连接                                                 │
│     ├─ 通信前必须建立连接（三次握手）                        │
│     ├─ 通信结束必须断开连接（四次挥手）                      │
│     └─ 通信双方维护连接状态                                  │
│                                                              │
│  2. 可靠传输                                                 │
│     ├─ 序列号：每个字节都有编号                              │
│     ├─ 确认应答（ACK）：接收方确认收到数据                    │
│     ├─ 超时重传：未收到 ACK 则重发                           │
│     └─ 数据排序：按序列号重组，保证顺序                      │
│                                                              │
│  3. 流量控制                                                 │
│     ├─ 滑动窗口：接收方告诉发送方"我还能收多少"              │
│     └─ 防止发送方淹没接收方                                  │
│                                                              │
│  4. 拥塞控制                                                 │
│     ├─ 慢启动：连接初期少量发送，逐步加速                    │
│     ├─ 拥塞避免：检测到拥塞则减速                            │
│     └─ 防止网络整体崩溃                                      │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 三次握手（建立连接）

```
客户端                                    服务器
  │                                         │
  │  ① SYN, seq=x                          │
  │ ─────────────────────────────────────→ │  我要连你
  │                                         │
  │              ② SYN+ACK, seq=y, ack=x+1 │
  │ ←───────────────────────────────────── │  好的，我准备好了
  │                                         │
  │  ③ ACK, ack=y+1                        │
  │ ─────────────────────────────────────→ │  收到，开始通信
  │                                         │
  │           ═══ 数据双向传输 ═══          │
  │                                         │
```

**为什么是三次而不是两次？**

```
两次握手的问题：
├─ 客户端发送的旧 SYN 延迟到达服务器
├─ 服务器回复 SYN+ACK，连接建立
├─ 但客户端根本不想连接了
└─ 服务器白白浪费资源维持一个无效连接

三次握手的解决：
├─ 第三次握手（客户端 ACK）确认了"客户端确实想连"
├─ 如果客户端没回 ACK，服务器不会真正建立连接
└─ 双方都确认了对方的接收和发送能力
```

### 2.3 四次挥手（断开连接）

```
客户端                                    服务器
  │                                         │
  │  ① FIN, seq=u                          │
  │ ─────────────────────────────────────→ │  我没数据了
  │                                         │
  │              ② ACK, ack=u+1            │
  │ ←───────────────────────────────────── │  知道了，等我一下
  │                                         │
  │             （服务器可能还有数据要发）   │
  │             ③ FIN, seq=v               │
  │ ←───────────────────────────────────── │  我也发完了
  │                                         │
  │  ④ ACK, ack=v+1                        │
  │ ─────────────────────────────────────→ │  好的，再见
  │                                         │
  │  （等待 2*MSL 后真正关闭）              │
  │                                         │
```

**为什么挥手要四次？**

```
TCP 是全双工的（双向都能收发数据）：
├─ 客户端说"我不发了"（FIN）→ 服务器回 ACK
├─ 但服务器可能还有数据要继续发
├─ 服务器发完后也说"我不发了"（FIN）→ 客户端回 ACK
└─ 所以需要四次：FIN-ACK ... FIN-ACK

对比握手：
├─ 握手时服务器把 SYN 和 ACK 合并为一次发送（SYN+ACK）
├─ 挥手时服务器的 ACK 和 FIN 通常不能合并（中间可能还有数据）
└─ 所以握手三次，挥手四次
```

### 2.4 TCP 的代价（游戏视角）

```
TCP 的可靠性是有代价的：

├─ 头部开销：20 字节（UDP 仅 8 字节）
│
├─ 实时性差：丢包 → 等待重传 → 阻塞后续包
│   └─ 一个包丢了，后面已到达的包也要等（队头阻塞）
│   └─ 对实时游戏致命：旧位置数据阻塞新位置数据
│
├─ 拥塞控制：网络不好时主动降速
│   └─ 游戏想发多少就发多少，TCP 自己偷偷减量了
│
├─ 连接建立慢：三次握手 + 慢启动
│   └─ 首包延迟高（尤其是 HTTPS 还要 TLS 握手）
│
└─ 结论：实时游戏（FPS/MOBA/动作）优先考虑 UDP 或可靠 UDP
```

## 三、UDP 深入

### 3.1 UDP 核心特性

```
UDP（用户数据报协议）— 无连接、不可靠

┌──────────────────────────────────────────────────────────────┐
│                       UDP 核心特性                           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 无连接                                                   │
│     ├─ 不需要建立连接，直接发数据                            │
│     ├─ 没有连接状态维护                                      │
│     └─ 发送开销极低                                          │
│                                                              │
│  2. 不可靠                                                   │
│     ├─ 不保证送达（可能丢包）                                │
│     ├─ 不保证顺序（可能乱序）                                │
│     ├─ 不保证不重复（可能重复到达）                          │
│     └─ 发出去就不管了（fire and forget）                     │
│                                                              │
│  3. 轻量                                                     │
│     ├─ 头部仅 8 字节                                         │
│     ├─ 没有流量控制 / 拥塞控制                               │
│     └─ 应用层自己决定可靠性策略                              │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 可靠 UDP（游戏常用）

```
UDP 不可靠，但游戏需要部分可靠性 → 可靠 UDP（Reliable UDP）

思路：UDP 传输 + 应用层实现可靠性

┌──────────────────────────────────────────────────────────────┐
│                  可靠 UDP 实现方案                            │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  核心机制（在应用层重新实现 TCP 的部分功能）：               │
│  ├─ 序列号：标识每个包                                       │
│  ├─ ACK 确认：接收方回确认                                   │
│  ├─ 超时重传：未收到 ACK 则重发                              │
│  └─ 滑动窗口：控制发送速率                                   │
│                                                              │
│  与 TCP 的关键区别：                                         │
│  ├─ 不强制队头阻塞：重要的包重传，不重要的包丢弃             │
│  ├─ 可选可靠性：关键消息可靠，位置更新允许丢包               │
│  ├─ 无拥塞控制：不会偷偷降速（自己控制发送频率）            │
│  └─ 更低的延迟：不需要等待序号连续                           │
│                                                              │
│  常见实现：                                                  │
│  ├─ KCP：纯算法协议，快速可靠，游戏常用（参考价值最高）      │
│  ├─ ENET：C 语言库，可靠+不可靠通道                          │
│  └─ LiteNetLib：C# 轻量 UDP 库，Unity 常用                   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**KCP 的核心优化**（游戏行业最常用的可靠 UDP）：

```
KCP vs TCP 的延迟对比：

TCP 丢包恢复：
  丢包 → RTO 超时（通常 200ms+）→ 重传 → 后续包解除阻塞
  总延迟增加：200ms+

KCP 丢包恢复：
  丢包 → 快速模式（RTO × 1.5，通常 30-60ms）→ 重传
  总延迟增加：30-60ms

KCP 的代价：
  ├─ 发送冗余包（更快的重传 = 更多的带宽消耗）
  ├─ 纯算法层，需要自己处理底层的 UDP 收发
  └─ 比同场景 TCP 多 10%-20% 带宽
```

## 四、HTTP/HTTPS 基础

### 4.1 HTTP 请求模型

```
┌──────────────────────────────────────────────────────────────┐
│                   HTTP 请求/响应模型                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  客户端（Unity）                  服务器                      │
│                                                              │
│  ① 构造请求 ──────────────────→                              │
│  POST /api/login HTTP/1.1                                    │
│  Host: game.example.com                                     │
│  Content-Type: application/json                             │
│  {"username": "player1", "token": "xxx"}                    │
│                                                              │
│                                 ② 处理请求                   │
│                                                              │
│  ③ 接收响应 ←──────────────────                              │
│  HTTP/1.1 200 OK                                            │
│  Content-Type: application/json                             │
│  {"code": 0, "data": {"playerId": 12345}}                   │
│                                                              │
└──────────────────────────────────────────────────────────────┘

特点：
├─ 请求-响应模型：一问一答，不是双向通信
├─ 无状态：每次请求独立（Cookie/Token 维持会话）
├─ 文本协议：可读性好但体积偏大（HTTP/2 改为二进制）
└─ 基于 TCP：底层使用 TCP 连接
```

### 4.2 常见状态码

| 状态码 | 含义 | 游戏开发场景 |
|--------|------|-------------|
| **200** | 成功 | 正常响应 |
| **201** | 已创建 | 创建角色、上传存档 |
| **204** | 无内容 | 删除操作成功，无返回体 |
| **400** | 请求错误 | 参数校验失败 |
| **401** | 未授权 | Token 过期、未登录 |
| **403** | 禁止访问 | 权限不足、封号 |
| **404** | 未找到 | 资源不存在 |
| **429** | 请求过多 | 限流、防刷 |
| **500** | 服务器错误 | 后端 bug |
| **502/503** | 网关错误 | 服务器维护中 |

### 4.3 RESTful API 简述

```
REST 风格：用 HTTP 方法表达操作意图

GET    /api/players/12345        → 获取玩家信息
POST   /api/players              → 创建玩家
PUT    /api/players/12345        → 更新玩家（全量）
PATCH  /api/players/12345        → 更新玩家（部分）
DELETE /api/players/12345        → 删除玩家

游戏常用接口模式：
├─ /api/login              POST   登录
├─ /api/upload             POST   上传存档/截图
├─ /api/config             GET    拉取游戏配置
├─ /api/pay/verify         POST   支付验证
└─ /api/ranking            GET    排行榜
```

### 4.4 Unity 中使用 HTTP

```csharp
using UnityEngine;
using UnityEngine.Networking;
using System.Threading.Tasks;
using System.Text;

// GET 请求
public static async Task<string> GetAsync(string url)
{
    using (var request = UnityWebRequest.Get(url))
    {
        request.SetRequestHeader("Authorization", "Bearer " + authToken);
        request.timeout = 10;

        await request.SendWebRequest();

        if (request.result == UnityWebRequest.Result.Success)
        {
            return request.downloadHandler.text;
        }

        Debug.LogError($"HTTP GET 失败: {request.error}");
        return null;
    }
}

// POST JSON 请求
public static async Task<string> PostJsonAsync(string url, object payload)
{
    string json = JsonUtility.ToJson(payload);
    byte[] body = Encoding.UTF8.GetBytes(json);

    using (var request = new UnityWebRequest(url, "POST"))
    {
        request.uploadHandler = new UploadHandlerRaw(body);
        request.downloadHandler = new DownloadHandlerBuffer();
        request.SetRequestHeader("Content-Type", "application/json");
        request.SetRequestHeader("Authorization", "Bearer " + authToken);
        request.timeout = 10;

        await request.SendWebRequest();

        if (request.result == UnityWebRequest.Result.Success)
        {
            return request.downloadHandler.text;
        }

        Debug.LogError($"HTTP POST 失败: {request.error}");
        return null;
    }
}
```

> **HTTP vs 长连接的选择**：休闲游戏（登录、存档、排行）用 HTTP 短连接即可；实时游戏（对战、聊天）需要 TCP/WebSocket 长连接。

## 五、WebSocket 原理

### 5.1 为什么需要 WebSocket

```
HTTP 的局限：
├─ 单向：只有客户端能发起请求
├─ 短连接：每次请求完就断开（HTTP/1.1 keep-alive 有改善但仍非双向）
└─ 实时性差：服务器有新数据时无法主动推送

变通方案（HTTP 轮询）：
├─ 短轮询：客户端每隔 N 秒发一次请求（浪费带宽和服务器资源）
├─ 长轮询：请求挂起，服务器有数据才返回（占连接资源）
└─ SSE（Server-Sent Events）：服务器单向推送（不能客户端→服务器）

WebSocket 的解决：
├─ 全双工：双向同时收发
├─ 长连接：一次握手，持续通信
├─ 低开销：握手后数据帧头部仅 2-14 字节
└─ 基于 TCP：可靠传输
```

### 5.2 WebSocket 握手过程

```
客户端                                          服务器
  │                                               │
  │  ① HTTP 升级请求                              │
  │  GET /ws HTTP/1.1                             │
  │  Upgrade: websocket                           │
  │  Connection: Upgrade                          │
  │  Sec-WebSocket-Key: dGhlIHNh...               │
  │ ────────────────────────────────────────────→ │
  │                                               │
  │  ② HTTP 101 Switching Protocols               │
  │  HTTP/1.1 101                                 │
  │  Upgrade: websocket                           │
  │  Connection: Upgrade                          │
  │  Sec-WebSocket-Accept: s3pPLM...              │
  │ ←──────────────────────────────────────────── │
  │                                               │
  │  ③ WebSocket 双向通信（不再是 HTTP）          │
  │  ←→ 二进制数据帧 ←→                           │
  │                                               │
  │  ④ 关闭帧 / TCP 断开                          │
  │                                               │
```

**关键特点**：WebSocket 握手时用 HTTP（能穿越大多数防火墙/代理），握手成功后协议升级为 WebSocket（不再是 HTTP）。

### 5.3 游戏中的 WebSocket 适用场景

| 场景 | 是否适合 WebSocket | 原因 |
|------|:---:|------|
| **WebGL 游戏** | 非常适合 | WebGL 不支持原生 Socket，WebSocket 是唯一长连接方案 |
| **休闲游戏** | 适合 | H5/小游戏平台通用，穿透性好 |
| **重度实时对战** | 勉强 | 基于 TCP，有队头阻塞问题；不如 UDP/KCP |
| **聊天系统** | 非常适合 | 文本双向通信，延迟要求不高 |
| **推送通知** | 非常适合 | 服务器主动推送 |

## 六、网络基础设施概念

### 6.1 DNS（域名系统）

```
DNS 作用：域名 → IP 地址

玩家设备                        DNS 服务器           游戏服务器
    │                               │                    │
    │  game.example.com 的 IP？     │                    │
    │ ────────────────────────────→ │                    │
    │                               │                    │
    │  ← 203.0.113.50              │                    │
    │                               │                    │
    │  连接 203.0.113.50 ──────────────────────────────→│

游戏开发注意：
├─ DNS 解析有延迟（首次 50-200ms，之后有缓存）
├─ Unity 中 UnityWebRequest 自动处理 DNS
├─ Socket 连接时传入域名也会自动解析
├─ DNS 劫持/污染：某些地区可能解析到错误 IP
└─ HTTPDNS：绕过系统 DNS，直接通过 HTTP 接口获取 IP（防劫持）
```

### 6.2 CDN（内容分发网络）

```
CDN 作用：将静态资源缓存在全球各节点，就近访问

无 CDN：
玩家（中国） ──→ 服务器（美国）   延迟 200ms+

有 CDN：
玩家（中国） ──→ CDN 节点（中国）  延迟 10-30ms
                  │
                  └── 未命中时回源 ──→ 服务器（美国）

游戏开发中的 CDN：
├─ 热更新资源：AB 包/YooAsset 资源放 CDN
├─ 图片/视频：头像、CG 动画
├─ 配置文件：版本号、服务器列表
├─ CDN URL 形式：https://cdn.game.com/bundles/xxx.bundle
└─ 配合云存储：S3/OSS 存源文件，CDN 做分发
```

### 6.3 NAT（网络地址转换）

```
NAT：多台设备共享一个公网 IP

┌─────────────────────────────────────────┐
│  家庭网络（192.168.1.x）                │
│                                         │
│  手机 192.168.1.10 ──┐                  │
│  电脑 192.168.1.11 ──┼── 路由器/NAT     │
│  主机 192.168.1.12 ──┘   ↓              │
│                     公网 IP 203.0.113.5 │
└─────────────────────────────────────────┘

NAT 对游戏的影响：
├─ 出站连接：NAT 自动处理，无感知
├─ 入站连接：外部无法直接连内部设备（P2P 的障碍）
│
└─ NAT 穿透方案（P2P 游戏需要）：
   ├─ UPnP：路由器自动开放端口（不是所有路由器支持）
   ├─ STUN：通过 STUN 服务器发现自己的公网映射
   ├─ TURN：通过中继服务器转发（最后的兜底方案）
   └─ ICE：综合 STUN + TURN 的协商框架
```

> **休闲游戏一般不需要 NAT 穿透**，因为用 C/S 架构，客户端只做出站连接。P2P 游戏或语音通话才需要。

## 七、游戏网络架构概览

### 7.1 C/S（客户端/服务器）架构

```
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 客户端 A  │  │ 客户端 B  │  │ 客户端 C  │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │             │             │
     └─────────────┼─────────────┘
                   │
          ┌────────┴────────┐
          │   专用服务器     │
          │  （权威状态源）  │
          └─────────────────┘

特点：
├─ 服务器是权威（authoritative），客户端只是"显示器"
├─ 安全性高：客户端作弊不影响其他玩家
├─ 成本高：需要维护服务器
├─ 适用：绝大多数商业游戏（MMO/MOBA/FPS/休闲）
```

### 7.2 P2P（点对点）架构

```
┌──────────┐         ┌──────────┐
│ 玩家 A    │ ←─────→ │ 玩家 B    │
│ (主机)    │ ←─────→ └──────────┘
└──┬───────┘
   │ ↕
┌──┴───────┐
│ 玩家 C    │
└──────────┘

特点：
├─ 一个玩家做主机（host），其他玩家连主机
├─ 无需专用服务器，成本低
├─ 主机玩家有延迟优势（不公平）
├─ NAT 穿透复杂
├─ 适用：格斗游戏、合作游戏、小规模对战
```

### 7.3 同步模型对比

```
┌──────────────────────────────────────────────────────────────┐
│                   帧同步 vs 状态同步                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  帧同步（Lockstep / Deterministic）                          │
│  ├─ 传输内容：玩家输入（按键、摇杆）                         │
│  ├─ 客户端各自模拟，结果必须完全一致（确定性）               │
│  ├─ 带宽消耗：低（只传输入）                                 │
│  ├─ 回放：天然支持（只需回放输入序列）                       │
│  ├─ 要求：严格的浮点数确定性（Unity 中很难）                 │
│  └─ 适用：RTS、格斗游戏（StarCraft、王者荣耀）               │
│                                                              │
│  状态同步（State Synchronization）                           │
│  ├─ 传输内容：游戏对象的状态（位置、血量、属性）             │
│  ├─ 服务器计算结果，广播给客户端                             │
│  ├─ 带宽消耗：高（每个对象都要同步状态）                     │
│  ├─ 回放：需要额外录制（快照+增量）                         │
│  ├─ 要求：不需要浮点数确定性                                 │
│  └─ 适用：FPS、MMO、MOBA（CS、LOL、原神）                    │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 八、常见网络问题

### 8.1 延迟（Latency / Ping）

```
延迟 = 数据从 A 到 B 的往返时间（RTT）

物理极限（光速）：
├─ 北京到上海（1300km）：约 4.3ms 单程
├─ 北京到洛杉矶（10000km）：约 33ms 单程
├─ 实际网络路径更长，经过路由器转发，延迟更高
└─ 实际经验值：同城 5-20ms，跨省 20-50ms，跨国 100-300ms+

游戏体感：
├─ < 30ms：流畅（几乎无感）
├─ 30-80ms：良好（休闲游戏可接受）
├─ 80-150ms：明显延迟（FPS/MOBA 开始影响体验）
├─ 150-300ms：严重延迟（操作滞后明显）
└─ > 300ms：几乎不可玩
```

### 8.2 丢包（Packet Loss）

```
丢包 = 数据包在传输过程中丢失

原因：
├─ 网络拥塞：路由器缓冲区满，丢弃溢出的包
├─ 信号干扰：Wi-Fi/移动网络不稳定
├─ 路由变化：网络路径变更导致包丢失
└─ 硬件故障：网线/路由器问题

影响：
├─ TCP：自动重传（但导致延迟增加、队头阻塞）
├─ UDP：数据直接丢失（游戏表现为卡顿/瞬移）
└─ 可靠 UDP：应用层重传（KCP 等方案）

容忍策略：
├─ 重要数据（登录、交易）：必须可靠
├─ 高频数据（位置同步）：允许丢失（最新的位置包最重要）
└─ 音视频流：允许丢失（丢一帧不影响大局）
```

### 8.3 抖动（Jitter）

```
抖动 = 延迟的波动量

正常网络：
  包1: 30ms → 包2: 31ms → 包3: 30ms → 包4: 32ms（稳定）

高抖动网络：
  包1: 30ms → 包2: 80ms → 包3: 10ms → 包4: 100ms（忽快忽慢）

影响：
├─ 角色移动不平滑（忽快忽慢/瞬移）
├─ 动画播放异常
└─ 输入响应不稳定

解决方案：
├─ 插值（Interpolation）：在两个已知位置间平滑过渡
├─ 外推（Extrapolation）：根据速度预测未来位置（可能不准）
├─ 抖动缓冲区（Jitter Buffer）：延迟一点显示，换取平滑性
└─ 实质：用少量延迟换取画面平滑度
```

### 8.4 粘包（TCP 专属问题）

```
粘包：多个消息粘连在一起接收

发送端发了 3 条消息：
  [消息A] [消息B] [消息C]

接收端可能收到：
  情况1：[消息A] [消息B] [消息C]      ← 正常
  情况2：[消息A + 消息B] [消息C]       ← 粘包
  情况3：[消息A + 消息B + 消息C]       ← 全粘

原因：TCP 是字节流，没有"消息边界"概念

解决：长度前缀法（见 [[【教程】Socket编程基础]] 粘包处理章节）

UDP 无此问题：UDP 保留数据报边界，一个 send 对应一个 recv
```

## 九、协议选择决策树

```
                    需要网络通信？
                         │
                    ┌────┴────┐
                    │         │
              需要实时        不需要实时
              双向通信        （请求-响应）
                    │              │
              ┌─────┴─────┐   ┌───┴───┐
              │           │   │       │
          WebGL/       原生平台   HTTP   HTTPS
          小游戏        │     │       │
              │     ┌────┴────┐ │ 加密用 HTTPS
         WebSocket   │      │ │
                     TCP    UDP/KCP
                  （回合制/  （实时对战/
                   聊天）    FPS/MOBA）
```

| 游戏类型 | 推荐协议 | 理由 |
|----------|----------|------|
| 休闲单机（云存档） | HTTPS | 短连接即可，无需实时 |
| 回合制/棋牌 | TCP | 可靠有序，延迟不敏感 |
| 聊天/社交 | WebSocket/WebSocket | 全双工，穿透性好 |
| MOBA/FPS | UDP/KCP | 低延迟，容忍丢包 |
| WebGL 游戏 | WebSocket | WebGL 不支持原生 Socket |
| MMO | TCP（非战斗）+ UDP（战斗） | 混合方案 |
