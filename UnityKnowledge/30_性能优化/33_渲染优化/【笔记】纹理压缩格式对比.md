## GPU 纹理压缩基础原理

### 与传统压缩的本质区别

传统图像压缩（PNG、JPEG、WebP）和 GPU 纹理压缩解决的是**完全不同的问题**：

| 维度 | 传统压缩（JPEG/PNG） | GPU 纹理压缩（DXT/ASTC/ETC） |
|------|----------------------|-------------------------------|
| **解压方式** | CPU 软件解码，整图解压 | GPU 硅片硬件解码，按需解压 |
| **访问模式** | 顺序读取，必须从头解到尾 | **随机访问**，任意像素 O(1) 取出 |
| **压缩比率** | 可变比率（VBR），复杂区域占更多空间 | **固定比率（FBR）**，每块占用固定字节数 |
| **使用场景** | 存储、传输 | 实时渲染采样 |

**为什么不能直接用 JPEG/PNG？**

GPU 采样纹理时需要随机访问任意位置的像素——一个三角形可能只覆盖纹素的局部区域。如果用 JPEG，GPU 要读取像素 (512, 512) 就得把整张图从头解压到该位置，这是 O(n) 操作，无法满足 60FPS 实时渲染的需求。

GPU 纹理压缩的设计目标就是：**给定任意 坐标，GPU 能在常数时间 O(1) 内解压出该像素颜色**。

### Block-based 压缩核心思想

所有主流 GPU 纹理压缩格式都采用同一基础架构——**分块编码（Block-based Encoding）**：

```
原始纹理 (W × H)
┌────┬────┬────┬────┬────┐
│ B1 │ B2 │ B3 │ B4 │ ...│  ← 每块固定大小（通常 4×4 像素）
├────┼────┼────┼────┼────┤
│ B6 │ B7 │ B8 │ B9 │ ...│  ← 每块独立压缩，互不依赖
├────┼────┼────┼────┼────┤
│ ...│ ...│ ...│ ...│ ...│
└────┴────┴────┴────┴────┘

块内数据结构：
┌─────────────────────────┐
│  端点色 A  │  端点色 B   │  ← 少量"代表色"
├─────────────────────────┤
│  索引表（每像素 2~4 bit）│  ← 每像素选哪个插值
└─────────────────────────┘

还原时：pixel = lerp(endpoint_A, endpoint_B, index / max_index)
```

**关键设计**：
- 每块独立压缩 → 可以随机访问任意块
- 固定字节数/块 → 内存布局可预测，地址计算 = 基地址 + 偏移量
- 块内插值 → 用极少数据（2 个端点 + 索引）还原 16 个像素

## 各格式算法原理

### DXT / BC（S3TC 系列）

**起源**：S3 Graphics 于 1998 年提出 S3TC，后纳入 DirectX 称为 DXT（DirectX Texture），OpenGL 中称为 BC（Block Compression）。至今仍是 PC 平台的标准格式。

#### BC1（DXT1）— 最基础版本

```
4×4 像素块 → 压缩为 64 bit（8 字节）

布局：
┌───────────────────────────────────────┐
│ color_0 (RGB565) │ color_1 (RGB565)  │  ← 2 个 16bit 端点色
├───────────────────────────────────────┤
│ lookup_table (32 bit)                │  ← 16 个 2bit 索引（4×16=32）
└───────────────────────────────────────┘

每像素 2bit 选择 4 种颜色之一：
  00 → color_0
  01 → color_1
  10 → 2/3 × color_0 + 1/3 × color_1
  11 → 1/3 × color_0 + 2/3 × color_1

结果：每像素 0.5 字节（4bpp），仅支持 RGB 无 Alpha
```

#### BC3（DXT5）— 带 Alpha 通道

```
= BC1 (RGB) + BC4 (Alpha) 独立压缩
┌──────────────────────────────┐
│ alpha_0..alpha_1 (16 bit)   │  ← Alpha 端点
│ alpha_index (48 bit)         │  ← 16 个 3bit Alpha 索引
├──────────────────────────────┤
│ color_0..color_1 (32 bit)    │  ← RGB 部分同 BC1
│ lookup_table (32 bit)        │
└──────────────────────────────┘
总计 128 bit / 16 像素 = 8bpp
```

#### BC7 — 现代高质量版本（DirectX 11+）

```
128 bit / 块，支持 RGB + Alpha

关键改进：
- 多种分区模式（8 种）：一块可分 1~2 个子集，各自独立插值
- 端点精度可变（4~8 bit per channel）
- 索引精度可变（2~4 bit）
- 支持 sRGB、预乘 Alpha

结果：质量显著优于 BC1/BC3，但仅 DX11+/现代 GPU 支持
```

| 格式 | 比特率 | 通道 | 质量 | 适用场景 |
|------|--------|------|------|----------|
| BC1 (DXT1) | 4bpp | RGB | 中 | 漫反射贴图、不透明纹理 |
| BC3 (DXT5) | 8bpp | RGBA | 中高 | 带透明通道的纹理 |
| BC4 | 4bpp | 单通道 | 中 | 高度图、遮罩图 |
| BC5 | 8bpp | 双通道 | 中高 | 法线贴图（XY 存储） |
| BC6H | 8bpp | RGB HDR | 高 | HDR 环境图、天空盒 |
| BC7 | 8bpp | RGBA | 很高 | 高质量颜色贴图、次世代 |

### PVRTC（PowerVR Texture Compression）

**起源**：Imagination Technologies 为 PowerVR GPU 设计，曾是 iOS 设备的唯一硬件压缩格式（ASTC 出现之前）。

#### 核心算法：双图混合

PVRTC 与其他分块格式**根本不同**——它同时维护两张低分辨率的"虚拟图"：

```
4bpp 模式（每像素 4 bit）：

原始纹理 → 拆分为两张图：
┌─────────────────┐    ┌─────────────────┐
│   Image A        │    │   Image B        │
│ (颜色信息)       │    │ (颜色信息)       │
│ 分辨率 = 原图/4  │    │ 分辨率 = 原图/4  │
└─────────────────┘    └─────────────────┘
          ↘                    ↙
           ┌─────────────────┐
           │  调制图 (Modulation) │
           │ 每像素 1 bit:        │
           │   0 → 取 Image A     │
           │   1 → 取 Image B     │
           │   插值 → A/B 混合    │
           └─────────────────┘
                    ↓
           双线性上采样 + 混合
                    ↓
              还原原始纹理

2bpp 模式：类似，但每像素仅 2 bit 调制信息
```

**算法特点**：
- 优点：对平滑渐变（天空、皮肤）表现好；压缩率灵活（2bpp/4bpp）
- 缺点：
  - 块效应明显——锐利边缘和细节区域出现"糊状"伪影
  - 仅支持正方形纹理（宽高必须为 2 的幂）
  - 仅 PowerVR GPU 硬件支持
  - 质量在同比特率下通常不如 ETC2/ASTC

**现状**：已被 ASTC 全面取代，仅作为旧设备（iPhone 4s 及更早）的兼容回退。

### ETC / ETC2（Ericsson Texture Compression）

**起源**：爱立信于 2005 年提出 ETC1，后扩展为 ETC2/EAC，成为 OpenGL ES 3.0+ 强制标准，Android 平台的事实标配。

#### ETC1 基础原理：两个基础色 + 亮度抖动

一句话：**把 4×4 块切成两半，每半存一个"代表色"，每个像素在代表色上叠加一个微小亮度偏移。**

```
4×4 块切两半（1 bit 决定水平切还是垂直切）：

  ┌──────┬──────┐
  │ 左半  │ 右半 │   每半块只需存：
  │      │      │   ├─ 1 个基础色（代表这个半块的"底色"）
  └──────┴──────┘   └─ 每像素 2 bit 索引 → 从亮度偏移表选一个值

64 bit 布局：
┌────────┬────────┬──────┬───────────────┐
│ 左半色  │ 右半色  │ 表号  │ 16×2bit 索引  │
│ 24bit  │ 16bit  │ 3bit │   32bit       │
└────────┴────────┴──────┴───────────────┘

亮度偏移表（共 8 张表，3 bit 选一张）：
  表0: {-8, -2, +2, +8}       ← 偏移小，适合颜色均匀的区域
  表4: {-60, -18, +18, +60}   ← 偏移大，适合颜色变化大的区域
  表7: {-183, -57, +57, +183} ← 极端偏移

还原：pixel = clamp(基础色 + 偏移值)
结果：64 bit / 16 像素 = 4bpp，仅 RGB
```

**为什么 ETC1 效果有限？** 两半各只有一个基础色，如果块内颜色复杂（渐变、多色），两个"代表色"无法覆盖。

#### ETC2 的核心技巧：利用"无效编码"免费获得新模式

ETC2 没有改块大小，也没有加 bit，而是发现了一个巧妙的"漏洞"：

```
ETC1 差分模式中，右半色 = 左半色 + RGB333 差值（范围 -4~+3）
  → 如果差值算出来是 -5 或 +4，ETC1 认为这"不可能发生"

ETC2 的做法：
  → 如果差值超出合法范围 → 这不是 bug，是"暗号"
  → 用这些"不可能的状态"触发三种新的压缩模式
  → 零成本扩展！不增加任何额外 bit
```

#### 三种新模式（通俗版）

```
┌──────────────────────────────────────────────────────────┐
│ T-mode：一个"异类"                                        │
│                                                            │
│   块内大部分是颜色 A，但有个别像素是颜色 C（明显不同）      │
│   ┌──┬──┬──┬──┐                                           │
│   │A │A │C │A │   存 3 种颜色：A（主）、B（近 A）、C（异类）│
│   │A │A │C │A │   每像素选 A/B/C 之一                      │
│   └──┴──┴──┴──┘   适合：暗背景上的亮点、纹理细节           │
├──────────────────────────────────────────────────────────┤
│ H-mode：两团颜色                                           │
│                                                            │
│   块内有两簇截然不同的颜色交错分布                          │
│   ┌──┬──┬──┬──┐                                           │
│   │A │B │B │B │   存 2 个颜色对（A0,A1）和（B0,B1）         │
│   │A │A │A │B │   每像素属于 A 组或 B组，各自插值            │
│   └──┴──┴──┴──┘   适合：两种颜色交错的边界区域             │
├──────────────────────────────────────────────────────────┤
│ Planar-mode：平滑渐变                                      │
│                                                            │
│   块内颜色沿对角线平滑过渡                                  │
│   ┌──┬──┬──┬──┐                                           │
│   │亮│ ↓ │ ↓ │暗│   只存 3 个角的颜色（左上、右上、左下）   │
│   │ ↓│   │   │ ↓│   其他像素 = 三角双线性插值               │
│   │暗│ ↓ │ ↓ │??│   pixel = f(C00, C01, C10, x, y)        │
│   └──┴──┴──┴──┘   适合：天空、阴影过渡、光照渐变           │
└──────────────────────────────────────────────────────────┘
```

**Planar-mode 为什么重要？** ETC1 的"基础色 + 偏移"本质上是恒定色 + 噪声，无法表达渐变。Planar 用 3 个角就能完美还原任意线性渐变——这是 ETC2 质量提升的关键。

#### Alpha 通道：EAC 独立编码

```
ETC2 本身只有 RGB。Alpha 通道用另一个 EAC 块编码：

EAC = 单通道版本的 ETC（64 bit / 4×4 块）
├─ 2 个 8bit 基础值
├─ 1 个 5bit 修饰表索引（16 张表）
└─ 16 × 3bit 索引（每像素选一个偏移）

ETC2 + EAC = 64 + 64 = 128 bit / 16 像素 = 8bpp
```

| 格式 | 比特率 | 通道 | 说明 |
|------|--------|------|------|
| ETC1 | 4bpp | RGB | 两半块 + 亮度偏移，无 Alpha |
| ETC2 | 4bpp | RGB | 新增 T/H/Planar 三种模式 |
| ETC2 + EAC | 8bpp | RGBA | Alpha 用 EAC 独立编码 |
| EAC | 4bpp | 单通道 | 高度图、遮罩图 |

**ETC2 编码优先级**：压缩器对每块尝试全部 4 种模式（标准/T/H/Planar），选误差最小的。

### ASTC（Adaptive Scalable Texture Compression）

**起源**：ARM + AMD 联合开发，2012 年成为 Khronos 标准。被设计为统一所有平台的"终极格式"。

#### 核心创新：128 bit 固定，块尺寸可变

```
所有格式中唯一支持可变块尺寸的：

┌──────────┬───────┬────────┬──────────────┐
│ 块尺寸    │ bpp   │ 压缩率  │ 通俗理解      │
├──────────┼───────┼────────┼──────────────┤
│ 4×4      │ 8.00  │ 75%    │ 几乎无损       │
│ 6×6      │ 3.56  │ 91%    │ 推荐性价比     │
│ 8×8      │ 2.00  │ 95%    │ 中等           │
│ 12×12    │ 0.89  │ 98%    │ 极端压缩       │
└──────────┴───────┴────────┴──────────────┘

数学本质：bpp = 128 ÷ (宽 × 高)
  块越大 → 每像素分到的 bit 越少 → 质量越低但体积更小
  一个参数就能在全画质范围内滑动
```

#### 128 bit 里装了什么

一句话：**配置信息 + 颜色端点 + 权重索引，三部分按需分配 bit，极其灵活。**

```
┌─────────────────────────────────────────────┐
│              128 bit 总预算                   │
│                                             │
│  ┌─────────┐  ┌──────────┐  ┌────────────┐ │
│  │ 配置位   │  │ 颜色端点  │  │ 权重索引    │ │
│  │ ~14bit  │  │ ~40bit   │  │ ~70bit     │ │
│  └─────────┘  └──────────┘  └────────────┘ │
│                                             │
│  配置位告诉 GPU 这块的三选一：                │
│  ├─ 几个分区？（1 或 2）                     │
│  ├─ 端点用什么编码？（14 种模式）              │
│  ├─ 权重网格多精细？（2~4 bit 精度）          │
│  └─ 是否双平面？（RGB 和 Alpha 分开插值？）    │
└─────────────────────────────────────────────┘
```

#### 四大精妙设计（通俗版）

**1. 颜色端点——不是直接存 RGB，而是"按需选编码"**

```
端点 = 一对颜色（端点 A 和端点 B），像素在两者间插值

ASTC 有 14 种端点编码方式，按需选择最省 bit 的：

  模式 0：直接存 RGB888     → 精度最高，最贵
  模式 6：RGB + Alpha=255   → 不透明纹理省掉 Alpha 的 bit
  模式 4：只存亮度（灰度）   → 灰度图只花很少 bit
  模式 3：端点A + 差值      → 两端点接近时只存差值，省空间

→ 压缩器根据这个块的特点选最省的编码
→ ETC2/DXT 只有一种编码方式，没有这个自由度
```

**2. 权重网格——存的不是每像素的权重，而是低分辨率"权重点阵"**

```
普通格式（DXT/ETC2）：每像素存 2bit 索引 → 直接查表

ASTC：存一个比块小的"权重网格"，双线性上采样得到每像素权重

  4×4 块 → 存 3×3 权重网格（只有 9 个值）
  ┌───────┐         ┌──────────────┐
  │ 3×3   │  双线性  │ 4×4 像素权重  │
  │ 9个值  │ ──插值→ │ 16个值（还原）│
  └───────┘         └──────────────┘

→ 只存 9 个权重而非 16 个 → 省 bit
→ 代价：权重精度略降（但视觉上几乎不可见）
→ 省下的 bit 用来提高端点精度 → 整体质量更好
```

**3. 分区——一块当两块用**

```
如果 4×4 块内有两团截然不同的颜色：

传统格式（DXT/ETC2）：2 个端点勉强覆盖两团颜色 → 质量差

ASTC 分区：把块分成 2 个区域，各自有独立的端点对

  分区图案 #42（棋盘格）：
  ┌──┬──┬──┬──┐
  │A │B │A │B │   A 区：端点对 (A0, A1)
  │B │A │B │A │   B 区：端点对 (B0, B1)
  │A │B │A │B │   → 两团颜色各自得到精确表达
  └──┴──┴──┴──┘

2048 种分区图案可选（11 bit 索引）
压缩器自动找最匹配块内颜色分布的图案
```

**4. 双平面——RGB 和 Alpha 各走各的路**

```
普通格式：1 套权重 → RGBA 四通道一起插值

  问题：树叶纹理
    RGB = 绿色平滑渐变（需要平滑权重）
    Alpha = 0/1 硬边轮廓（需要突变权重）
    → 一套权重无法兼顾

ASTC 双平面：2 套独立权重
  平面 0 → 插值 R, G, B（可以用平滑权重）
  平面 1 → 插值 A（可以用突变权重）

  代价：两套权重平分 bit → 每套精度减半
  收益：RGB 和 Alpha 各自最优 → 不再被迫折中
```

#### 压缩器的决策过程

```
ASTC 解码是固定的（GPU 硬件实现），压缩是自由的——
不同压缩器（astcenc / Unity / ISPC）质量差异很大。

每块的压缩决策树：
1. 分析块内颜色分布
   ├─ 平滑渐变？ → 用高精度端点 + 高精度权重
   ├─ 两团颜色？ → 用分区模式
   ├─ RGB 和 A 分布不同？ → 用双平面
   └─ 颜色简单？ → 省端点 bit，留给权重

2. 尝试多种组合，计算重建误差

3. 选误差最小的组合
   → fast 模式：少试几种（快但质量略低）
   → thorough 模式：穷举所有组合（慢但质量最高）
```

#### 为什么 ASTC 是未来标准

```
ETC2 是"少而精"：4 种固定模式，编码空间小，简单可靠
ASTC 是"多而灵活"：参数自由组合，编码空间巨大，质量上限高

┌────────────┬─────────────────┬──────────────────────┐
│            │ ETC2             │ ASTC                 │
├────────────┼─────────────────┼──────────────────────┤
│ 块尺寸     │ 固定 4×4         │ 4×4 ~ 12×12 可选     │
│ 比特率     │ 固定 4bpp        │ 0.89~8 bpp 可选      │
│ 编码模式   │ 4 种（固定）      │ 参数组合（数百种）    │
│ 质量上限   │ 中等（4bpp 封顶）│ 8bpp 接近无损         │
│ Alpha      │ 需额外 EAC 块    │ 内置，无额外开销      │
│ HDR        │ 不支持           │ 支持                  │
│ 硬件要求   │ GLES 3.0+       │ GLES 3.2+ / iOS A8+  │
│ 压缩器差异 │ 小（模式有限）    │ 大（参数空间巨大）    │
└────────────┴─────────────────┴──────────────────────┘
```

**一句话**：ETC2 像一把固定扳手（简单够用），ASTC 像一个万能工具箱（灵活强大但需要更好的 GPU 硬件来解码）。

## 质量特征与伪影

每种压缩格式都有典型的失真模式（artifact / 伪影），理解这些有助于针对性优化：

| 格式 | 典型伪影 | 视觉表现 | 最差场景 |
|------|----------|----------|----------|
| **DXT/BC1** | 块边界、色阶 | 颜色过渡出现阶梯、4×4 块交界处可见 | 平滑渐变（天空盒）、精细法线 |
| **DXT/BC3** | Alpha 块效应 | 透明边缘锯齿、半透明区域阶梯 | UI 圆角、柔和半透明 |
| **BC7** | 极少伪影 | 接近无损，块效应极低 | 基本无弱点 |
| **PVRTC** | 糊状模糊 | 锐利边缘溶解、细节区域模糊 | 文字、图标、高频细节 |
| **ETC2** | 色彩偏移 | 深色区域颜色漂移、块边界微弱可见 | 高对比度边缘、暗部细节 |
| **ASTC** | 轻微块效应 | 高 bpp 时几乎无伪影；低 bpp 时出现块状 | 12×12 极端压缩下细节丢失 |

### UI 纹理 vs 3D 纹理的不同要求

```
UI 纹理需求：
├─ 锐利边缘（文字、图标） → 对糊状伪影零容忍
├─ 精确 Alpha（圆角、阴影）→ 需要 Alpha 通道高质量
├─ 通常尺寸小（256×256 ~ 1024×1024）
└─ 推荐：ASTC 4×4 或不压缩（UI 对包体不敏感时）

3D 纹理需求：
├─ 可接受一定模糊（人眼会"脑补"）
├─ 法线贴图需要高质量（影响光照精度）
├─ 通常尺寸大（1024×1024 ~ 4096×4096）
└─ 推荐：颜色 ASTC 6×6 / ETC2；法线 BC5 / ASTC
```

## Unity 实践要点

### 纹理类型与压缩格式的对应关系

Unity 的 Texture Importer 中，不同 Texture Type 可选的压缩格式不同：

| Texture Type | 推荐压缩格式 | 不能使用的格式 |
|-------------|-------------|---------------|
| **Default**（颜色贴图） | ASTC / ETC2 / BC7 / DXT5 | — |
| **Normal Map**（法线贴图） | BC5 / DXT5(BC3) / ASTC | DXT1(无Alpha) |
| **Sprite (2D and UI)** | ASTC / RGBA16 | Crunch 压缩**不建议**用于 UI（解压有损+慢） |
| **Single Channel**（遮罩） | BC4 / EAC / ASTC | ETC1(仅RGB) |
| **Cubemap**（天空盒） | BC6H(HDR) / ASTC / BC7 | PVRTC(不支持非2幂) |

### Crunch 压缩补充说明

Unity 提供的 Crunch 压缩（Crunched DXT/ETC）是在 GPU 压缩格式之上再加一层类似 JPEG 的 **可变比率有损压缩**，用于减小包体：

```
原始纹理 → GPU格式(如DXT5) → Crunch再压缩 → 更小的存储文件
                                       ↓
                          运行时 CPU 解Crunch → 恢复为DXT5 → GPU采样
```

- 优点：包体减小 50%~70%（下载更快）
- 缺点：加载时需要 CPU 解压（额外耗时），质量二次损失
- 适用：颜色贴图、不追求极致加载性能的场景
- **不适用**：UI Sprite（增加加载时间且 Alpha 质量下降）、法线贴图

### Build Settings 中的平台覆写

Unity 允许为每个平台单独设置压缩格式：

```
Texture Importer → Platform overrides:
┌──────────────────────────────────────┐
│ Platform    │ Max Size │ Format      │
├────────────┼──────────┼─────────────┤
│ Default    │ 2048     │ RGBA Compressed │
│ iOS        │ 2048     │ ASTC 6x6    │  ← 可独立设置
│ Android    │ 2048     │ ETC2        │  ← 可独立设置
│ PC         │ 4096     │ BC7         │  ← 可独立设置
│ WebGL      │ 2048     │ ETC2/DXT    │
└────────────┴──────────┴─────────────┘
```

也可通过 `AssetBundle` 变体（variant）为不同设备分发不同质量的纹理。

### Android 设备兼容性分水岭

```
Android GPU 压缩支持时间线：

OpenGL ES 2.0 设备
├─ ETC1 ✓（仅 RGB，无 Alpha）
├─ ETC2 ✗
├─ ASTC  ✗
└─ PVRTC ✗（仅 PowerVR GPU）
→ 仅能用 ETC1 + 单独 Alpha 通道

OpenGL ES 3.0+ 设备（2013年后，API 18+）
├─ ETC2 ✓ ← 强制支持
├─ EAC  ✓
└─ ASTC  ✗（取决于 GPU）

OpenGL ES 3.2+ / Vulkan 设备（2015年后）
├─ ETC2 ✓
└─ ASTC  ✓ ← 强制支持（GLES 3.2 起标配）
```

**Unity Android 策略**：
- Minimum API Level ≤ 17：ETC2 可能不被支持，需 fallback 到 ETC1
- Minimum API Level ≥ 18：ETC2 全线支持，安全使用
- 若 Minimum API Level ≥ 24 且仅支持 Vulkan：可直接用 ASTC
- 实践折中：**默认 ETC2，高端设备分包用 ASTC**

### iOS ASTC 支持情况

```
iOS ASTC 硬件支持：
├─ Apple A7（iPhone 5s, iPad Air）  → ✗ 不支持
├─ Apple A8（iPhone 6, iPad mini 4）→ ✓ 支持 ASTC
├─ Apple A9+                        → ✓ 支持
└─ Apple A11+（iPhone 8+）          → ✓ 全面支持 ASTC + HDR 变体

结论：
- Deployment Target ≥ iOS 11（iPhone 6s+）→ ASTC 全线可用
- 需兼容 iPhone 5s → 回退 PVRTC 4bpp
- 2026 年实践：可安全默认 ASTC（5s 早已停止支持）
```
