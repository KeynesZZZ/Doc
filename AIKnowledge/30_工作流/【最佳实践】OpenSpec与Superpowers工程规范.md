# OpenSpec与Superpowers工程规范

> 策划只交付设计文档并回答业务问题；程序把方案翻译成可验证、可追踪的工程规格，再用 Superpowers 完成开发与自测。规范化的复杂度全部封装在程序侧，对策划和 QA 透明。

## 大前提

整套责任划分建立在一个明确前提上：**策划只提供设计文档，负责回答开发中的业务问题，验收依据是「设计文档 + 开发前已确认的理解」**。策划不编辑 OpenSpec、不写 Scenario、不维护任何工程工件。

因此「把模糊意图变成明确行为」这件事完整落在程序侧。这不是负担转移，而是让职责变干净——只要配套的确认环节到位，验收阶段就不会失控。

- OpenSpec 是程序把产品文档转化为可靠实现的**规格中间层**。
- Superpowers 是执行这个工程规格的**开发流程**（brainstorming、writing-plans、TDD、调试、审查、分支收尾）。

## 三条设计原则

| 原则 | 含义 |
|------|------|
| 最小强制、按风险加码 | 只有四个产物强制存在，其余按需求风险等级启用 |
| 边界靠物理隔离 | 工具职责重叠靠目录规则和模板强制，不靠制度文字和自觉 |
| 派生物可重新生成 | 面向 QA、验收的文档一律从规格导出并标注来源版本，不手工维护副本 |
| 状态拆维度不拉长 | 用规格/实现/验收三个独立维度描述进度，而非发明复合状态 |

## 角色边界

三个角色里只有程序碰工件；策划和 QA 全程只用自然语言输入输出。

| 角色 | 输入 | 输出 | 碰工件 |
|------|------|------|--------|
| 策划（业务负责人） | 程序提出的业务问题 | 设计文档、问题答复、验收结论 | 否 |
| 程序（工程负责人） | 设计文档、策划答复 | OpenSpec 全部工件、提测说明、自测证据 | 是 |
| QA（测试负责人） | 提测说明、导出行为基线 | 测试结论、缺陷 | 否 |

每个 Change 在 `proposal.md` 顶部固定三个具名责任人，让问题总有人关闭。权威冲突（文档、口头确认、OpenSpec、配置表不一致）时，由业务负责人在约定时限内裁决，结论写入 `proposal.md` 决策记录，注明时间和来源——即「谁、多久、留在哪」三要素。

## 四个强制产物

任何需求都必须产出且仅必须产出这四样，其余按风险启用。

| 强制产物 | 对应 OpenSpec 工件 | 为什么不能省 |
|----------|--------------------|--------------|
| 需求来源与有效版本 | `proposal.md` 顶部来源块 | 冲突时唯一的仲裁依据 |
| 可验证的行为规格 | `specs/` | 自测和 QA 的共同基线 |
| 唯一任务清单 | `tasks.md` | 防止出现第二套任务系统 |
| Requirement—Test 验证证据 | `tasks.md` 内嵌或自测报告 | 让「通过」变成可核对的事实 |

`design.md`、详细执行计划、验收行为表、生命周期跟踪与影响分析，**不是每个需求都做**，按分级规则启用。

## 三档分级流程

分级线必须客观可判定，依据是需求触及的系统风险，而非主观难度。

| 档位 | 触发条件（客观） | 必需产物 |
|------|------------------|----------|
| 完整流程 | 触及玩家资产、付费、存档、协议、经济数值、跨端兼容、安全 中任一 | 四强制产物 + `design.md` + 影响分析 + 验收行为表 + 三维生命周期 |
| 标准流程 | 新功能或行为变更，不触及上述高风险项 | 四强制产物 + 按需 `design.md` |
| 轻量流程 | 内部重构、局部低风险修复、文案或纯展示配置 | 来源 + 预期行为 + 影响范围 + 验证方式 |

硬性约束：涉及协议、存档、经济数值、付费、安全、跨端兼容或玩家资产的修改，**无论看起来多小都走完整流程**。

## 核心闭环：翻译回确认

在「策划只给文档」的前提下，这是防止验收阶段大规模返工的唯一低成本机制，且必须是准入门槛，不是可选礼节。

断链办法是在开发前让策划确认**程序的理解**，而不是确认 OpenSpec 本身。程序把 Scenario 反向翻译成策划能读的自然语言，策划只回答「对/不对」和填补空白：

```text
# 程序理解确认（策划只读、只回答业务问题）
关于“按品质批量分解”，我的理解是：
1. 选择蓝色品质时，选中所有蓝色可分解装备
2. 蓝色但已锁定的装备不被选中
3. 已穿戴装备不出现在可选范围
4. 背包满时……（文档没写，需要你定）

请确认 1–3，并回答第 4 条。
```

文档没写到的边界，按「是否影响玩家可感知结果」一刀切：

| 边界类型 | 默认归属 | 举例 |
|----------|----------|------|
| 影响玩家资产/结果/体验 | 必须策划确认 | 背包满怎么处理、材料发不发 |
| 纯技术内部行为 | 程序自决并记录 | 超时重试几次、幂等键设计 |
| 展示细节 | 程序自决，策划可事后否决 | 预览列表排序、提示文案 |

每问一个业务问题、每回答一次，结论就写进 `proposal.md` 决策记录。**验收时的「已确认理解」就是这些决策记录的集合**，既是验收基线，又不产生会漂移的副本。

## 三维生命周期

真实项目常出现部分开发、分批测试、灰度发布、多端进度不一致。解决办法不是拉长状态链，而是把一个 Change 拆成三个独立维度：

| 维度 | 取值 | 含义 |
|------|------|------|
| 规格状态 | Draft / Ready / Locked | 行为基线是否已确认 |
| 实现状态 | 未开始 / 部分完成 / 完成 | 代码进度，可按 Task 粒度 |
| 验收状态 | 未验收 / 策划通过 / QA 通过 | 质量确认进度 |

归档与上线解绑：**归档 = 规格基线更新事件**（specs 合并进主规格）；**上线 = 发布事件**（灰度、全量、观察期）。做法是 QA 通过即可归档以固化规格基线，上线单独用发布记录跟踪；生产问题回写时新开 Change 引用原 Change，而不是复活已归档历史。

准入门槛不等于全部等待。问题分阻塞（未确认不开发）、非阻塞（带默认结论开发）、后续（另建需求）三类，等待期间先做不依赖未决规则的基础工作，并在 `tasks.md` 标记被**冻结**的任务。

## OpenSpec 与 Superpowers 边界

只要 Superpowers 输出被长期保存，就容易形成第二套设计和计划。用物理规则隔离：

```text
openspec/changes/<change>/     ← 唯一正式工件，进版本库
  proposal.md
  specs/
  design.md        （按风险启用）
  tasks.md         （唯一任务清单）

.superpowers/ 或临时工作区       ← 执行展开，不进版本库，随分支销毁
  plan-<task-id>.md
```

一句话规则：Superpowers 的 `writing-plans` 产物是某个 Task 的**一次性执行脚本**，绑定 Task ID、可随时丢弃；一旦它开始描述「项目要做什么」，就说明内容放错地方，应回填 `tasks.md` 或 `design.md`。

## 缺陷与需求变更分类

有了「文档 + 已确认理解」双基线，验收分歧可以被干净归类：

| 验收/测试发现 | 判定与处理 |
|---------------|------------|
| 实现和已确认理解不符 | 实现缺陷，程序修，规格通常不变 |
| 实现符合确认，但策划改主意 | 需求变更，更新文档和决策记录后再改 |
| 文档和确认当时都没覆盖 | 新发现需求，补确认后决定当前改或另开 Change |
| 程序理解偏离原始文档且没确认过 | 翻译缺陷，且暴露确认环节被跳过（最危险） |
| 用例与有效规格不一致 | 测试缺陷，改测试 |
| 代码正确但配置/线上数据异常 | 修配置或数据，评估是否补防御逻辑 |

最需要盯的是第四行：一旦出现「程序理解错了又没让策划确认」，说明「翻译回确认」被省了，这是本前提下最危险的失败模式，所以该步必须是强制准入项。

## 落地顺序

先启用四强制产物与三档分级，再按团队实际情况引入影响分析与三维生命周期跟踪。不要一开始全面实施，避免中小需求的文档成本接近开发成本。

## 在 Claude Code 里的实际操作

日常开发在 Claude Code 中进行时，本规范不改内容，但落地形态从「人工写工件」调整为「在工具命令之间插人工卡点」。三层各司其职：

| 层 | 谁触发 | 在 Claude Code 里的形态 |
|----|--------|------------------------|
| OpenSpec | 你显式敲斜杠命令 | `/opsx:explore`、`/opsx:propose`、`/opsx:apply`、`/opsx:archive` |
| Superpowers | **自动触发** | 说「开始做」后自动 brainstorming → writing-plans → TDD → code-review，无需敲命令 |
| 本规范 | 人工卡点 | 分级判定、翻译回确认、提测/归档前校验——没有命令会替你做 |

> 命令前缀是 `opsx`（不是 `opx`）；生成 proposal 的命令是动词 `/opsx:propose <change-name>`，不是 `/opsx:proposal`，且一条命令会同时生成 proposal + specs + design + tasks 四件套。

### 一次需求的操作序列

1. **分级判定**（手动，10 秒）：碰玩家资产/付费/存档/协议/经济/跨端/安全 → 完整流程；普通功能 → 标准；文案/重构 → 轻量。决定后面是否保留 `design.md`。
2. `/opsx:propose <change-name>`：一次生成四件套；轻量档可删掉 `design.md`。
3. **翻译回确认**（手动，规范命脉）：把生成的 Scenario 用大白话贴给策划确认，补「三责任人 + 决策记录」进 `proposal.md`，规格才从 Draft 转 Ready。跳过这步 = 规范失效。
4. `/opsx:apply` 后放手让 Superpowers 接管：它自动拆计划、派 subagent 逐个 Task 做、强制 TDD、任务间自动 code-review。你只做 review 确认。
5. **提测/验收**（手动卡点）：校验 Requirement—Task—Test 无缺口才提测；策划按「文档 + 已确认理解」验收；QA 依据导出行为基线测试。
6. `/opsx:archive`：把 specs 合并进主规格；上线用发布记录单独跟踪。

### 两个安装与边界细节

- OpenSpec 与 Superpowers 是两个独立插件，各装各的：OpenSpec 走 `openspec init`，Superpowers 走 Claude 插件市场 `/plugin install superpowers@claude-plugins-official`，两者不共用命令前缀。
- 默认只有 `explore` 和 `propose` 两个入口命令；要用 `/opsx:verify`、`/opsx:continue` 等扩展命令需先 `openspec config profile` 切扩展档再 `openspec update`。其中 `/opsx:verify` 可辅助「提测前校验」卡点。
- Superpowers 的 writing-plans 产物是某个 Task 的一次性执行脚本，不进版本库；正式工件永远只有 `openspec/changes/<change>/` 四样。靠 `.gitignore` 和习惯守住，工具不会自动分。

## 如何喂产品文档（文字 + 图片）

产品文档是描述性的、有留白的。**不要直接把整份文档甩给 AI 然后 `/opsx:propose`**——AI 会把留白按自己的猜测补成 Scenario，而这正是「翻译回确认」要拦住的最危险失败模式。文档是 `explore` 的输入，不是 `propose` 的输入。

正确顺序：

```text
产品文档（文字+图片）
  → 你把图里的关键规则读成文字要点
  → /opsx:explore  贴文档，让 AI 复述理解 + 列出文档没覆盖的边界问题
  → 拿这些边界问题找策划确认
  → /opsx:propose <change>  （输入 = 文档 + 已确认结论）
  → 翻译回确认，补决策记录，规格转 Ready
```

关于图片的关键坑：产品文档里的原型图、流程图、数值表截图包含大量规则信息，但 AI 对图片的理解不如纯文字可靠，尤其是**数值表、状态流转箭头、UI 标注**这类精确信息容易看错或漏看。因此关键规则（奖励数值、状态流转、边界条件）应由程序从图里读出、转成文字要点再喂给 AI；图片可作为参考附上，但不作为规格的唯一来源。「把图读成文字规则」本身就是程序「把方案翻译成可验证规格」职责的一部分。
